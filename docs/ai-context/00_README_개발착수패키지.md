## §9. 진행 규칙

### 9-1. "초안"과 "확정"을 구별하는 표식 — 발주자가 눈으로 확인할 수 있게

문서가 확정되면 **두 가지가 동시에** 바뀝니다. 둘 다 바뀌지 않았으면 아직 초안입니다.

1. 파일명에서 `_초안`이 빠집니다 — `01_M2_도메인계약_초안.md` → `01_M2_도메인계약.md`
2. 머리말 3줄 아래에 **`> 상태: 확정 v1.0 (2026-__-__)`** 한 줄이 붙습니다

> 확정 판정 기준(Claude 몫): 문서 안의 🔴·⚠️ 표시가 전부 해소되고, `01`의 경우 §8 미결 표에 「첫 과제를 막나 = 예」 항목이 남아 있지 않을 것. 확정 뒤에는 **`domain_contracts` 코드가 최종 정본**이고 문서는 설명이 됩니다.

### 9-2. 그 밖의 규칙

- 발주자 결정이 필요한 **새 쟁점은 임의로 정하지 않습니다** — 선택지 + 권고로 질문합니다(결정 1~9 방식).
- 각 단계가 끝나면 **청사진 아티팩트를 같은 URL로 갱신**하고 `10_리뷰/`의 스냅샷과 메모리(`invest-flutter-app-blueprint`)를 함께 갱신합니다.
- `06_시스템설계/` 편집 전에는 `git log -3`·`git status`로 병행 회차의 진행 중 작업이 없는지 확인합니다. `00_SPEC.md`는 **CRLF** — 편집 시 EOL을 유지합니다.
- 안전·마찰 화면에 대한 "UX 개선" 제안은 **거절이 기본값**입니다(핸드오프 §6).
- 오버엔지니어링 금지: 사용자 1인, 리밸런싱 월 1회급, 주문 연 ~934건 규모입니다. 확장성보다 **틀렸을 때 조용히 틀리지 않는 것**이 우선입니다.
