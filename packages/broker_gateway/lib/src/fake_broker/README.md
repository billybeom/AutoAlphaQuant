# `lib/src/fake_broker/` — FakeBroker 자리 안내 (🆕 E10b · 설계 13 §8 R33 D13 · R35 V9)

> 🔵 **이 폴더는 비어 있다 — 가짜 브로커는 두 층으로 나뉘어 다른 곳에 있다.**
> - **포트 수준**(순서기가 포트 응답에 어떻게 반응하는가) = `package:core_engine/testing.dart` 의 `FakeOrderBroker` · `FakeOrderLedger` — core_engine · data_sync · broker_gateway 시험이 같이 쓴다.
> - **전송 수준**(전송된 HTTP 요청 수 · F-14b S01~S13 · R32 O5 코드 · 07 §6-3 픽스처) = 이 패키지 `test/` 의 MockClient(E10d).
> - 🔴 엔진 내부 가상 체결(X6-3 · `simInternal` · E15)은 같은 포트의 **lib 구현**이지 FakeBroker 가 아니다(«모의 전용 분기 0» — 06 X6-3). 그래서 종전 «DRY_RUN·SIM 기간의 유일한 상대» 문장을 지웠다.

가짜 브로커는 실제 브로커를 부르지 않고 주문 경로 전체를 돌려보기 위한 것이다. 골든벡터가 «계산이 맞는가»를 보는 것과 달리 여기는 **«이상한 응답이 왔을 때 무너지지 않는가»**를 본다.

## 담을 시나리오(포트 수준 ✅ E10b 일부 · 전송 수준 = E10d)

| 갈래 | 시나리오 |
|---|---|
| 정상 | 전량 체결 · 부분 체결 · 지연 체결(FILL_LAG) |
| 거부 | 주문유형 화이트리스트 밖(SAF-404) · 잔고 부족 · 장 마감 |
| 모호 | 응답 유실 후 재조회에서 체결 확인(UNKNOWN 해소) · 타임아웃 |
| 방어 | 같은 멱등키 재발주 → **`prevented`**(NR-1이 작동한 것) |
| 장애 | 토큰 만료 · 유량 초과 · 브로커 5xx 연속 |

## 🔴 규칙

1. **실키·실계좌를 쓰지 않는다.** 응답도 합성값이다.
2. **`prevented`를 실패로 만들지 않는다** — 이중 발주 차단은 성공 경로다.
3. **모호한 응답을 «실패»로 단정하지 않는다.** UNKNOWN은 해소 보드로 넘어가는 별도 상태다.
4. 이 폴더의 시나리오는 **DRY_RUN 이탈 판단의 근거가 아니다.** 그 게이트는 골든벡터(`core_engine/test/golden/`)다.
